From the engine to the product

The keystone is the assembly compiler: a robot file of kit parts becomes a sim model, the daemon's robot file, the kinematic chain and the robot's capabilities, and a checker gates it. The LLM and snap builders are editors on top. The reasoning is in build-plan.md.

A0

Addressable API: everything reachable by address

in progress

The key rule: every client (CLI, dashboard, later a remote one) talks to APIs by address and never depends on running locally. Then LexJR on the Mac to a Pi walker is a new address, not a rewrite.

effort ~1–2 weeksdepends on M00/8 tasks
  • gamerobotd: the same JSON-RPC over a WebSocket, localhost by default, next to the unix socket
  • Runner control API in the app: slots and owners, switch a behaviour, live parameter changes, load or save a personality
  • Supervisor status API in play: processes and their state, health messages, start and stop
  • The CLI uses these APIs (gamerobotctl and gamerobotics), so it is the first client
  • Jitter histogram in the daemon's state: tick period p50, p99 and worst, over the last minute
  • Guardrails: API servers on their own threads; one state encode a tick shared by all subscribers; slow clients drop frames; no video, meshes or logs on the control API; the runner's control API on its own thread
  • Measure: tick time and jitter unchanged with the dashboard subscribed at 20–50 Hz and intents streaming at 50 Hz
  • Tests: every dashboard action is possible through the APIs alone
Done when
  • Everything play's terminal shows and the camera preview's keys do is available through the APIs
  • The CLI works against them
  • Measured: the loop's tick time and jitter (p99, worst) are the same with the API in use as without
Risks
  • Scope creep into the parked remote access: no pairing or discovery yet, localhost only
  • A gateway or encoder slipping into the control thread: guarded by design and by the measurement

Hardware bring-up: LexJR tethered

to do

Every later choice (the parts catalogue's numbers, packaging, whether LexJR needs a Pi) depends on how the real robot behaves. Tethered over USB to the Mac, the Reachy Mini Lite way.

effort ~2–3 weeksdepends on M00/8 tasks

  • gamerobotd --io feetech, with the servo bus port and baud in the robot file
  • Servo setup per joint in the robot file: ID, zero, direction, ratio
  • Bench bring-up with one servo: ID, 7.4 V supply, torque on and off, a move
  • Calibration helper: torque off, move each joint by hand, read ticks, write zeros and directions
  • Measure: loop tick time and jitter on the real bus, command latency, gravity sag vs the sim, a BAM check on one servo
  • play lexjr on the real robot (a hardware target in the project), face follow and cat gaze
  • Record the measurements in the spec; update the sim where it disagrees
Done when
  • The real LexJR follows a face through gamerobotics play, tethered to the Mac
  • Measured timing, latency and sag are in the spec, and the sim's assumptions are checked against them
Risks
  • Power: servo current and the supply
  • Serial timing through the Waveshare board on macOS
M1

Parts catalogue and assembly compiler

to do

The keystone: every Build experience produces a robot file of kit parts, and this turns it into a running robot. Removes the LexJR hard-coding.

effort ~4–6 weeksdepends on M0, H00/7 tasks
  • Catalogue format: geometry and mesh, mass and inertia, mounts, actuator model, limits, modes
  • First parts: STS3215 (BAM moved out of sim_bam.py), spur N:1, brackets and links, wheel, webcam, IMU, battery and board
  • Compiler: robot file to MJCF, daemon robot file, chain, motion config, capabilities
  • Derived limits and speeds; gears as generated joint equalities
  • Generic sim body: run any compiled MJCF, one BAM model per actuator
  • Regression: LexJR as parts compiles to today's limits; golden replays pass
  • New robot: a pan-tilt head from the catalogue runs cat gaze and mimic tilt unchanged
Done when
  • LexJR recompiled from parts matches today (±57° torso, 183.3°/s) and passes the golden replays
  • A pan-tilt head written as a file runs the behaviours unchanged
Risks
  • Part geometry (brackets, links, mounts) is CAD work, not code
